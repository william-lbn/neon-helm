# PG18 新实例的共同运行权限接线

## 原因与修复

本轮 PG18 使用独立 Compute cp-24c41e23bb104ead。原部署只登记了 PG17 的配置 Secret 与 SQL Service，新实例需要登记自己的具名资源。

资格采集首先被 Kubernetes 拒绝读取 cp-24c41e23bb104ead-config。通过既有 dsga-qualifier-access Chart 为该实例增加具名 get 后，原正式采集器完成收集，独立签发器完成 26 项权限检查并签发资格。

正式 Proxy 路由已发布后，第一次应用连接收到 adapter_unavailable。原 neon-adapter 的 managedRuntimeRead.computes 仅包含 PG17。给同一列表增加 PG18 的 configSecretName 与 serviceName 后，Helm neon-pg17-adapter 第 6 版只更新 Role，实际应用连接成功。

## 共同合同

两项均复用现有 Chart 和配置结构。部署者按实例登记准确的资源名，PG 大版本由下层发行输入与原生能力表达。Agent、Scheduler、Runner、Proxy 继续使用同一版本化协议。

新实例发布顺序应包含具名读取权限预检。先准备原 Runtime/Runner 与配置 Secret，登记 Collector 的配置读取权，完成真实资格采集与独立签发，再装载 Agent 来源和策略。发布正式 Proxy 路由前登记适配器的配置与 Service 读取权，随后以普通应用角色做真实连接。

## 实测

collector-access.PUBLIC.json 记录具名配置 get 通过，以及业务凭据读取、Secret 列表、配置更新被拒绝。proxy-access.PUBLIC.json 记录配置和 SQL Service 具名 get 通过，以及业务凭据读取、Secret 列表、配置更新被拒绝。

issuer.PUBLIC.json 记录 14 个允许与 12 个拒绝全部符合预期。完整原始材料分别位于 118 的 /data/neon-k8s-pg18/runs/PG18-独立实例具名资格读取授权-02679a05、PG18-正式Proxy具名运行读取接线-02679a05 和 PG18-同源资格采集签发-940b25fb。

本目录的 values 文件为本轮准确部署输入。PG18 四项内存与业务数据/WAL 的最终结果另行归档。
